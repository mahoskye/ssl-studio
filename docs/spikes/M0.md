## Language server (`spikes/m0-lsp/probe.ts`)

Capabilities: completion, definition, formatting, range formatting, document
and workspace symbols, folding, hover, inlay hints, references, rename,
signature help. **No** semantic tokens, **no** custom requests.

Document symbols already give the Objects panel what it needs: comment
regions come back as Namespace symbols with their procedures nested inside,
and parameters inside those.

Folding ranges include control-flow blocks (`:IF`, `:BEGINCASE`) and
`:REGION` bodies, but every range has kind `region` and no node type, and
statements are absent. Enough for region frames and procedure cards; not
enough for blocks mode. **L1 (syntax tree) is still needed.**

Timings (ms), first request after opening includes the parse:

| File | documentSymbol | foldingRange | full formatting |
| --- | --- | --- | --- |
| Fixture, 65 lines | 3 | 0.6 | 2.5 |
| Work script, 6,249 lines, 231 KB | 121 | 4 | 342 |
| Work script, 8,499 lines, 401 KB | 172 | 6 | 969 |

(The work scripts were read in place for timing only; nothing from them is
recorded here or committed.)

Formatting returns **one edit replacing the whole document** (range formatting:
the whole range). Applied as-is it moves the cursor and markers; the spike
trims it to the changed lines before applying, which keeps both. Format on
save on a 400 KB script would take about a second: format the changed ranges
instead.

Lessons for the app:
- Import `monaco-editor/editor/editor.api`, not the package root: the root
  pulls in TypeScript, CSS, HTML and JSON language workers (about 9 MB).
- The spike maps each token's innermost scope to a Monaco token type. That
  ignores descendant theme selectors; the app should use `tokenizeLine2`'s
  encoded tokens and the registry's colour map.
- The worker import path is `monaco-editor/editor/editor.worker?worker`
  (0.57's export map).

## Electrobun 2.x

- `electrobun@2.0.5` on npm is a bootstrap only (2.0.5 released 2026-10-26).
  It downloads Hutch (a launcher and build tool) and the Electrobun runtime
  from GitHub releases, verified by SHA-256 against an index in the package.
- `electrobun init` also runs Hutch's remote `install.sh` to put a global
  launcher in `~/.hutch`. It refused here because the bootstrap had already
  written its cache into `~/.hutch` (an ordering bug). Every other command
  runs from the private cache, so a hand-written project avoids the global
  install.
- The Solid template (copied to `spikes/m0-shell/` at tag v2.0.5) uses Vite,
  `electrobun/main` for `BrowserWindow`, and `views://` URLs. App APIs come
  from a projected `.hutch/devkit`, not `node_modules`.
- `electrobun prepare` (allowed by the user 2026-11-01) downloaded the
  Electrobun 2.0.5 core and a Bun 1.4.4 toolchain into `~/.hutch`, and
  projected the devkit into `.hutch/devkit`. The app runs its own bundled Bun,
  not the system one.
- `hutch install --frozen-lockfile` installs from `hutch.lock` with Hutch's
  own resolver, which **never runs install scripts** (it skipped one).
- `hutch electrobun dev` builds into `build/dev-linux-x64/` and launches.
  Application menus are not supported on Linux: the app draws its own.

## Window (`spikes/m0-shell/`)

The m0-editor page, unchanged except for its host: `web/selfcheck.ts` takes a
`Host` (file, big file, report, LSP transport), `web/main.ts` is the browser
host over HTTP and a WebSocket, and `spikes/m0-shell/src/mainview/main.ts` is
the Electrobun host over RPC. The Bun process spawns `starlims-lsp --stdio`
and passes one unframed JSON-RPC message per Electrobun message each way.
Assets (`onig.wasm`, the grammar, the Monaco worker) load from `views://`
without changes.

| Check | Electrobun window (WebKitGTK 2.52) | MiniBrowser, for comparison |
| --- | --- | --- |
| Highlighting, theme, worker, errors | ok, ok, ok, none | same |
| Completion / hover / diagnostics / format + undo | 524 items / yes / 3 / yes | same |
| Editor create | 115 ms | 113 ms |
| Tokenize all 6,250 lines | 161 ms | 154 ms |
| Switch to the 6,250-line file / first frame | 23 / 16 ms | 22 / 13 ms |
| Scroll, per 4,000 px jump | 19-20 ms | 18 ms |
| LSP round trips, fixture: hover / completion / formatting | 23-27 / 21-54 / 7-9 ms | 12 / 25 / 4 ms |
| LSP round trips, fixture: documentSymbol | 6-112 ms | 12-43 ms |

RPC echo, round trip, median of five: 1 KB 16 ms, 100 KB 16 ms, 1 MB 93 ms.
Electrobun encrypts each message (AES-GCM, per webview) over a loopback
socket and sends in batches, which looks like the source of the floor.

For the app:
- RPC is fine for the LSP. If completion feels slow while typing, the
  fallback is a direct loopback WebSocket from the Bun process with a
  per-launch token, as in m0-editor; the client already takes either.
- The LSP starts on the first message; initialize took about 200 ms
  including the spawn. Start it with the workspace, not on demand.

## opencode 2.2.5

From [opencode-api.md](opencode-api.md), with the three key claims checked
again by hand (`opencode serve --stdio` exists; `/api/info` returns 2.2.5;
`~/.claude/agents` holds the SSL agents and no opencode agent folder exists):

- Start a **private server**: `opencode serve --stdio --port 0` with a fresh
  `OPENCODE_PASSWORD`; it prints `{"url": ...}` and stops when stdin closes.
  No shared secret, no file reads. Attaching to the background service is an
  option.
- **Version** from `GET /api/info`; the OpenAPI document says `0.0.1`.
- **Prompts are asynchronous**; results arrive on the SSE stream, which does
  not replay, so the client resyncs from the message list after a drop.
- **Model is per session**, and the server default here is a paid OpenRouter
  model: the adapter must always set the model, local by default.
- **Permissions**: per-session rules deny `shell`, `webfetch`, `websearch`,
  `external_directory`, and `question` for unattended runs. `webfetch` was
  **enforced** on a real call; the others evaluate to deny, but no tool to
  exercise them was reachable (below).
- **Skills**: all 16 `ssl-*` skills load from `~/.claude/skills`.
  **The SSL agents do not**: v2 only reads `agents/` under its own config
  directories. That is the style guide's installer to fix, not the IDE. It
  may also bear on the cleanup runner failing on the remote machine.
- **Prompt results (2026-11-01)**, three prompts to `qwen3:14b` on this
  machine's Ollama, cost 0 (detail in opencode-api.md section 11):
  - The model got **code mode**: one `execute` tool running JavaScript with
    `fetch` and opencode's own helpers (worktrees, session rename and move,
    MCP resources), but **no file tools and no shell**. So the IDE should
    put the code in the prompt and apply the answer as range edits itself.
  - A denied action fails inside the tool with `Permission denied: <action>`;
    the turn carries on and `permission.asked` never fires.
  - The `question` tool opens a form and **waits for an answer
    indefinitely**: deny it for unattended runs or show the form.
  - A turn ends with `session.execution.succeeded | failed | interrupted`,
    not `session.idle`. Text streams as `session.text.delta`; usage comes
    with `session.step.ended` and `session.usage.updated`.
  - `OPENCODE_CONFIG_CONTENT` in the private server's environment pins a
    local model without touching the user's config. The configured `ollama`
    provider points at another machine, which was not answering.

## UI library: Solid

Not settled by building both; chosen because:
- plain TypeScript and JSX, so the standard compiler and editor tooling work
  without a second file format;
- fine-grained updates without a virtual DOM suit a blocks tree of thousands
  of nodes where one edit touches a few;
- Electrobun has a maintained Solid template.

Svelte 5 would do as well. Revisit only if blocks mode hits a wall.
