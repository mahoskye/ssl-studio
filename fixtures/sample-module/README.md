# Sample module

A small equipment-calibration application laid out like a STARLIMS v11 export:
one object of every kind an export contains, with the sidecar files an export
puts beside them. It is here as a workspace fixture for SSL Studio: open it
with `hutch run start fixtures/sample-module` and the IDE meets the real
layout, file kinds and language features it will see in a customer codebase.

The module was written fresh for the corpus project's fixture work and is
generated by that project's tools; nothing in it comes from a deployment, a
customer or a real export. Names, tables, readings and dates are invented. The
feature map in `FEATURES.md` ties every file to the rows of that project's
feature checklist.

## What the IDE does and does not open yet (2026-11-08)

- `.srvscr` and `.ds` open as SSL (`src/view/editor/monaco.ts`); the
  language server reads the server scripts and the SSL-bodied data source.
- SQL-bodied data sources (`EquipmentList.ds`, `UnitsLookup.ds`,
  `StatusCodes.ds`) are SQL with an SSL-style header; opened as SSL they
  show diagnostics on the query body.
- `.clientscript` and `.codeBehind` are JavaScript; the IDE has no mode for
  them yet.
- `.ENG.xfd` form definitions, `.ENG.Y` and `.ENG.N` resource sets and the
  `.res` global resources are XML; `.ENG.size.xfd` is `width,height`;
  `.ver` and `.comments` are one-line sidecars; `.privilege` is a one-line
  marker. The IDE has nothing for any of them yet, and must at least not
  choke on them in the file tree.
- `Server Scripts/SAMPLE_BROKEN/` holds eleven deliberately invalid scripts,
  one per defect class the export's own rejected files show; each should
  produce one diagnostic on the right line, and the question-mark case is
  the one a parser is tempted to report at the file's start.

## Running the module

The sandbox manifests under `manifests/`, the SQLite fixture under
`fixtures/` and the client-style requests under `requests/` run in the
STARLIMS sandbox project (`corpus-test --manifest`, `run --request`); the
form code-behind and client scripts run under the corpus project's Node
harness. None of that is needed to use the module as an IDE fixture.

## What is here

| Path | Kind |
|---|---|
| `Applications/SAMPLE_LAB/EQUIPMENT_CALIBRATION/` | One application: server scripts, data sources, two forms with code-behind and resources, a client script |
| `Server Scripts/SAMPLE_UTILITIES/` | Category-level helpers, including .NET interop and a privilege file |
| `Server Scripts/SAMPLE_BROKEN/` | One deliberately invalid script per defect class (checklist G2); the IDE's error-recovery cases |
| `Data Sources/SAMPLE_LOOKUPS/` | Category-level lookup queries |
| `Client Scripts/SAMPLE_LIB/` | A shared JavaScript library |
| `Global Resources/GlobalResource.ENG.res` | A small resource set |

Every object has a `.ver` and a `.comments` sidecar in the export's shape, with
synthetic content. Forms have `NAME.ENG.xfd` (the definition), `NAME.ENG.size.xfd`
(width and height), `NAME.codeBehind` (JavaScript) and `Form Resources/NAME.ENG.Y`
and `.ENG.N` (resources and translatable properties).

## Status

The server scripts are written and run in the sandbox:

- `Server Scripts/SAMPLE_UTILITIES/`: seven helper scripts, covered by the 56
  cases of `manifests/sample-utilities.json`.
- `Applications/SAMPLE_LAB/EQUIPMENT_CALIBRATION/Server Scripts/`: seven
  application scripts (lookup with a SQL region, validation with an error
  block, shared constants, a transactional save drawing a counter, a long
  scheduling script, a base class and a derived class with an include),
  covered by the 33 sequential cases of `manifests/sample-lab.json` on the
  `fixtures/sample_lab.sql` database, with state checks after each write.
- `SAMPLE_BROKEN` is complete by design.

The four data sources are written: three SQL-bodied (`@name` parameters from
the `:PARAMETERS` line, directives for connection, table name and null
handling, one with only a banner) and one SSL-bodied (a script whose
`:PARAMETERS` carry inline defaults). Server procedures run them through
`RunDS`, and `requests/` holds four client-style `GetData` and `GetDataSet`
requests. A data source's language is catalog metadata, so the manifest and
the requests name the SQL ones in `data_source_languages`.

The two data sources under the application are named
`EQUIPMENT_CALIBRATION.<Name>`, the form the export's own form code uses for
application data sources. The sandbox resolves that name since its ADR 0269
(pull request #58, merged 2026-11-08, closing issue #57); on an older
sandbox, the eight manifest cases and two requests that reach these data
sources fail with `Script not found! ... Type: DataSource`.

The two forms and two client scripts are written. The forms are XML in the
export's shape: typed controls with layout, anchors, a data-bound combo box
and grid, event hooks, a scripts list and per-form resources. Their
code-behind uses the runtime vocabulary the export's form code uses
(`Form.All`, `Form.Resources`, `Form.formArguments`, `Form.returnValue`,
`Form.Close`, `Form.DisplayWaitMessage`, `lims.CallServer`,
`lims.GetDataSource`, `lims.GetFormSource` with `Form.ShowModalDialog`, a
grid's `GetCurrentRowData`). The STARLIMS HTML runtime is not available
here, so `tools/sample_module_client_check.js` runs the handlers in Node
against mocked `Form` and `lims` objects and checks what they do; `--check`
runs it, plus `node --check` on every script and a well-formedness pass over
the XML.

The global resource set holds sixteen entries in the export's style
(CamelCase identifiers, label strings ending with a colon, messages with
`{0}` placeholders). The privilege file reproduces the shape of the export's
single example: one sixteen-byte line beside a server script. Neither has
behaviour to run; both are design-time files the IDE must open and keep.
